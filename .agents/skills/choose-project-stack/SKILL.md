# 选择技术方案

1. 先读README、AGENTS、brief、decisions、现有ADR、package/lockfile和最相关的源码。引用已确认答案；只问会改变选择的未知约束。优先复用现项目，禁止为了演示替换已可用架构。
2. 区分交付类型：游戏运行时需要比较适配的引擎或现有游戏架构；创作工作台比较网页/桌面、现系统复用或新增服务。不要因为样例游戏而凭空引入游戏引擎。
3. 仅列两到三个可实施方案。按 [比较表](references/compare.md) 比较维护成本、地区可用性、预算、数据与密钥边界、构建部署、可逆性。把「本机可预览」「他人设备可打开」「跨设备仍有数据」分别列为条件。
4. 用硬约束先排除不合格方案，再给推荐理由。私密密钥必须留在服务端或受保护运行环境；前端环境变量不提供秘密保护。需要共享数据时，说明权限、备份与恢复责任。
5. 当前价格、区域访问、供应商条款尚未查证时标记「待核验」，给验证动作。不要承诺永久免费、固定性能或部署已成功。优先用锁文件和官方拥有源核验版本，避免重复查已确认的信息。
6. 用 [ADR模板](assets/adr-template.md) 写采用方案、备选、理由、后果、迁移成本和复议触发条件。写明状态是建议、已采用或已验证；更新decisions的引用，不复制两套冲突规则。
7. 安排一个最小技术验证切片：在目标设备打开核心路径；若需共享，执行两个独立会话/设备写入读取与刷新恢复。记录实际结果后才更新验证状态。

讨论方法来源时读 [来源](references/sources.md)。遵守当前会话授权，产生可评审的ADR和验证步骤，不把选型当作部署许可。
