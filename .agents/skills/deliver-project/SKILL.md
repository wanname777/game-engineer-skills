# 推进项目交付

1. 读README、AGENTS、brief、decisions、tasks及验收记录；执行只读Git状态检查。识别现有修改与所有者，不覆盖他人工作。需要并行时声明各自文件所有权；没有明确必要不增加并行任务。
2. 选一个未阻塞的小切片，用 [任务模板](assets/tasks-template.json) 标明依赖、负责人、验收步骤和状态。已知前置未完成时保持阻塞；重新打开前置任务时复议下游验收和里程碑。
3. 实施最小完整用户路径，保留单一规则来源，去除无用代码和旧草稿。按项目约定维护短AGENTS与设计决策。实验功能使用隔离分支/工作区；保存Git节点、提交、推送、PR、发布遵循当前会话已有授权，不自作主张合并或部署。
4. 根据改动执行项目要求的检查。此项目行为改动执行 `npm run check`；动画改动额外执行 `npm run render:motion`。失败时定位原因，修复后重跑相关检查。报告命令、退出状态和可定位证据；未运行与运行失败分别记录。
5. 在真实浏览器走完整路径。工作台示例：打开 → 修改输入 → 生成预览 → 下载 → 操作任务 → 刷新检查持久化。按实际功能调整，禁止声称存在未实现的导入或云保存。检查桌面、手机、键盘、控制台错误与布局；记录步骤、视口、产物和结果。截图是辅助证据，不替代可操作行为。
6. 将本机预览、共享链接、跨设备数据、刷新/重启恢复分别验收。出现控制台错误或核心行为失败，不能把对应验收写成通过。生成链接不等于他人设备已访问。
7. 用 [验收记录模板](assets/acceptance-template.md) 更新任务证据与milestone。只有依赖满足且验收已执行才标完成。GitHub CI需要实际查看当前commit的检查；部署需要真实目标与结果，视频需要实际渲染文件。
8. 给出可审核改动、实际检查结果、未解决事项与下一步。若创建PR，描述最终行为和验证，不写研究过程。未经明确授权不使用工具向他人发消息。

需要证据分类时读 [证据规则](references/evidence.md)；讨论作者迁移时读 [来源](references/sources.md)。
